# Розгортання VERDE ERP

Покроковий регламент переходу з демонстрації в роботу. Розрахований на те, що
виконувати його буде людина без досвіду адміністрування — кожна команда
наводиться повністю.

Найбільша частина роботи тут не технічна, а перенесення ваших даних. Технічне
розгортання займає годину, дані — від кількох днів.

---

## Що знадобиться

- акаунт [Supabase](https://supabase.com) — база даних, безкоштовного тарифу вистачає на старт;
- акаунт [Vercel](https://vercel.com) — сам застосунок;
- доступ до репозиторію `lmshkherson/verde`;
- ваші дані: номенклатура, контрагенти, залишки складу, сальдо по рахунках.

---

## Крок 1. База даних

1. У Supabase створіть проєкт. Регіон беріть найближчий — Frankfurt.
2. Придумайте пароль до бази й **збережіть його в менеджері паролів**. Відновити його не можна, лише скинути.
3. Скопіюйте рядок підключення: **Project Settings → Database → Connection string → URI**.
   Беріть варіант із портом `6543` (pooler) — він тримає багато одночасних підключень.
4. Підставте пароль замість `[YOUR-PASSWORD]`.

Вийде щось на кшталт:

```
postgres://postgres.abcdefgh:ВашПароль@aws-0-eu-central-1.pooler.supabase.com:6543/postgres
```

## Крок 2. Схема й перший користувач

Локально, у теці `erp`:

```bash
npm install

export DATABASE_URL='postgres://...ваш рядок...'
npm run db:migrate
```

Далі — бойова ініціалізація. Вона створює юрособу, склади й вашого власника.
**Демо-даних і відомих паролів не створює.**

```bash
ADMIN_EMAIL='olena@v-verde.ua' \
ADMIN_NAME='Олена Ковальчук' \
ADMIN_PASSWORD='якийсь-довгий-унікальний-пароль' \
ENTITY_NAME='ТОВАРИСТВО З ОБМЕЖЕНОЮ ВІДПОВІДАЛЬНІСТЮ «ВЕРДЕ СВІТ»' \
ENTITY_SHORT='Верде Світ' \
ENTITY_PREFIX='ВС' \
ENTITY_EDRPOU='45014741' \
ENTITY_IPN='450147426573' \
ENTITY_VAT=true \
npm run db:init
```

Реквізити тут справжні — з виписки ЄДР і витягу з реєстру платників ПДВ
(форма 2-ВР). `ENTITY_NAME` пишіть саме так, як у виписці: ця назва друкується
в шапці накладних.

Пароль коротший за 12 символів скрипт не прийме.

Другу юрособу (ФОП) додасте потім в інтерфейсі на сторінці «Юрособи» — там же
задається префікс документів, він має бути свій.

Одразу після цього зайдіть на **Юрособи → Реквізити для друкованих форм** і
заповніть адресу, телефон, банк та підписанта. В обліку вони ні на що не
впливають, але без них бланк накладної друкується з прогалинами.

## Крок 3. Ваші дані

Шаблони CSV лежать у `db/templates/`. Заповніть їх в Excel і збережіть як CSV
UTF-8. Крапка з комою як роздільник і кома в числах — це нормально, імпорт таке
розуміє.

Порядок важливий: спершу довідники, потім залишки.

```bash
npm run db:import -- items      db/templates/номенклатура.csv
npm run db:import -- suppliers  db/templates/постачальники.csv
npm run db:import -- customers  db/templates/клієнти.csv
npm run db:import -- employees  db/templates/працівники.csv --entity 'Верде Світ'
npm run db:import -- stock      db/templates/залишки.csv     --entity 'Верде Світ'
npm run db:import -- balances   db/templates/сальдо.csv      --entity 'Верде Світ'
```

Перед справжнім запуском додайте `--dry-run` — покаже, скільки рядків
опрацюється, і нічого не змінить.

Кожен імпорт можна повторювати: він оновлює за ключем, а не дублює. Складські
залишки при повторі теж не подвоюються.

**Сальдо по рахунках** імпорт перевіряє окремо й скаже, якщо дебет не дорівнює
кредиту. Поки не сходиться — баланс у звітності не зійдеться теж.

Рецептури заводяться руками в інтерфейсі: їх небагато, а помилка в рецептурі
дорожча за годину набору.

Одразу після імпорту довідників зробіть дві речі, інакше перше ж приймання
стане:

1. **Постачальники → затвердити.** Імпорт заводить їх незатвердженими навмисно:
   перелік затверджених постачальників має з'явитися внаслідок оцінки, а не
   внаслідок імпорту. У картці кожного — прапорець, дата перегляду й підстава.
2. **Номенклатура → «Потребує вхідного контролю».** Поставте його на сировині й
   на пакуванні, що контактує з продуктом. Партії таких позицій ставатимуть у
   карантин до закриття акта вхідного контролю.

У картках контрагентів заповніть **IBAN**: за ним банківська виписка впізнає
платіж, коли ЄДРПОУ в рядку немає. Для клієнтів окремо є **адреса доставки** —
у мереж це розподільчий центр, і саме вона стає пунктом розвантаження в ТТН, а
юридична лишається в реквізитах.

**Поживні дані сировини** вносяться в картці позиції: білки, жири, вуглеводи,
цукри, волокна, сіль на 100 г — зі специфікацій постачальників, і там же
вказується джерело. Там же ставляться алергени. Поки в інгредієнта немає даних,
специфікація продукту з ним не затвердиться, а етикетку друкувати нема з чого.

Банківські рахунки заводяться на сторінці **Банк**: назва, IBAN, банк. Виписка
імпортується файлом або текстом — колонки система визначає сама.

План HACCP заводиться на сторінці **HACCP**: точки, межі, періодичність і
гранична пауза між записами. Демо-набір із семи точок є в `scripts/seed.mjs`,
але внести треба свій план — чужий перевірку не влаштує.

## Крок 4. Застосунок

1. У Vercel: **Add New → Project**, оберіть репозиторій, у полі **Root Directory** вкажіть `erp`.
2. Додайте змінні середовища:

| Змінна | Значення |
|---|---|
| `DATABASE_URL` | рядок підключення з кроку 1 |
| `SESSION_SECRET` | згенеруйте: `openssl rand -base64 32` |

`SESSION_SECRET` — це ключ, яким підписуються сесії. Слабкий ключ означає, що
вхід під власником можна підробити, тому в бойовому режимі застосунок просто не
запуститься з коротким чи очевидним значенням.

3. Натисніть **Deploy**.

### Якщо Node на вашому комп'ютері не встановлено

Кроки 2 і 3 вимагали запуску команд локально. Їх можна перекласти на Vercel:
він виконує їх під час складання, і встановлювати нічого не доведеться.

У **Settings → Build & Deployment → Build Command** увімкніть перевизначення й
вкажіть:

```
npm run db:migrate && npm run db:init && next build
```

Реквізити з кроку 2 (`ADMIN_EMAIL`, `ADMIN_NAME`, `ADMIN_PASSWORD`,
`ENTITY_NAME`, `ENTITY_SHORT`, `ENTITY_PREFIX`, `ENTITY_EDRPOU`, `ENTITY_IPN`,
`ENTITY_VAT`) додайте змінними середовища поруч із `DATABASE_URL`.

Після першого вдалого деплою **приберіть `ADMIN_PASSWORD`** зі змінних і
скоротіть команду до `npm run db:migrate && next build`. Міграції нехай
лишаються: вони застосовуються один раз кожна, тож наступні оновлення схеми
приїжджатимуть разом із деплоєм самі.

Для міграцій беріть **пряме** підключення Supabase (порт 5432), а не pooler:
через транзакційний pooler частина DDL не проходить. Для компанії на кілька
користувачів пряме підключення годиться і для звичайної роботи.

## Крок 5. Перевірка

Відкрийте `https://ваш-домен/api/health`. Має бути:

```json
{ "status": "ok", "database": "connected", "migrations": 32, "warnings": [] }
```

Якщо у `warnings` є демо-акаунти — деактивуйте їх:

```sql
update app_users set is_active = false where is_demo;
```

Далі увійдіть під власником і пройдіть коротким колом:

1. **Склад** — залишки збігаються з тим, що ви імпортували. Якщо складів
   більше за три типові — заведіть їх на «Склад → Склади» до імпорту залишків.
2. **Бухоблік** — задайте вхідні залишки, натисніть «Перегенерувати період», перевірте, що дебет дорівнює кредиту.
3. **Звітність** — актив дорівнює пасиву.
4. Заведіть по одному працівнику й основному засобу, щоб побачити нарахування.

## Бекапи

Supabase на платних тарифах робить їх сам, але **власний бекап робіть теж** —
відновлення чужими руками завжди довше.

```bash
pg_dump "$DATABASE_URL" -Fc -f verde-$(date +%F).dump
```

Відновлення:

```bash
pg_restore -d "$DATABASE_URL" --clean --if-exists verde-2026-08-09.dump
```

**Перевірте відновлення один раз до того, як воно знадобиться.** Візьміть
бекап, розгорніть у порожню базу, відкрийте `/api/health`. Бекап, який ніколи не
відновлювали, — це не бекап.

## Щомісячний регламент

Порядок має значення: проводки будуються з документів, тож спершу документи.

1. Закрити всі варки й відвантаження місяця. Раз на рік перед річним звітом —
   **інвентаризація**: опис по кожному складу, факт, закриття.
   Тоді ж перевірити **вхідний контроль**: чи не лишилися акти незакритими й чи
   не висить у карантині сировина, яку насправді давно перевірили. І **HACCP** —
   чи немає точок із простроченим моніторингом і відхилень без коригувальної дії.
2. **Банк** → імпортувати виписки за місяць і рознести чергу до нуля. Робити це
   першим має сенс: оплати міняють і дебіторку, і кредиторку, а виписку
   зручніше розбирати, поки пам'ятаєш платежі.
3. **Зарплата** → сформувати, провести, виплатити.
4. **Основні засоби** → нарахувати амортизацію.
5. **Фінрезультат** → внести оренду, енергію та інші витрати періоду.
6. **Повернення** → провести всі за місяць: від клієнтів (міняють дохід і ПДВ)
   та постачальникам (міняють запаси й податковий кредит).
7. **ПДВ** → виписати податкові накладні, зареєструвати їх, підготувати декларацію.
   Перевірте розрахунки коригування: ті, де реєструє покупець, самі не закриються.
   Потім **Обмін документами** → поставити ПН і РК у чергу й надіслати.
8. **Бухоблік** → «Перегенерувати період».
9. Перевірити: оборотка балансує, актив дорівнює пасиву, розбіжність між книгами пояснювана.

Якщо після генерації щось не сходиться — виправляйте документ, а не проводку.
Проводки перебудуються самі.

## Відкат

Розгортання оборотне на будь-якому кроці, крім імпорту даних.

- **Застосунок** — у Vercel: Deployments → попередній деплой → Promote to Production.
- **Схема** — міграції не мають зворотних скриптів, тож відкат схеми = відновлення з бекапу. Тому бекап перед міграцією обов'язковий.
- **Дані** — імпорт ідемпотентний, помилковий файл виправляється й заливається повторно.

## Поки що робиться поза системою

- реєстрація в ЄРПН і подача декларацій: документи формуються й ідуть у M.E.Doc або
  «Вчасно» чергою обміну, але квитанції система не читає — статус реєстрації
  відмічається вручну;
- накладення КЕП — у самому M.E.Doc чи «Вчасно»;
- реєстрація розрахунків коригування: система їх складає й показує, хто подає,
  але подання так само йде через M.E.Doc або «Вчасно»;
- електронна ТТН: бланк друкується, е-обмін із КЕП — через «Вчасно»;
- лабораторні дослідження: протоколи вносяться як документ на партію, але
  замовлення й отримання результатів іде поза системою;
- аудит постачальника: система тримає рішення й дату перегляду, сама оцінка —
  анкета, аудит, документи — робиться поза нею.

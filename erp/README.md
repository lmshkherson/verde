# VERDE ERP

Облікова система виробництва натуральних батончиків: склад, виробництво, закупівлі, продажі.

Next.js 15 (App Router, серверні дії) + Postgres. Працює однаково на локальній базі
й на Supabase — застосунок ходить у Postgres напряму драйвером `pg`.

## Головний принцип

Залишок ніде не зберігається окремим числом. Є журнал рухів `stock_moves`, куди
пишуться прихід, списання у варку, випуск, відвантаження, інвентаризація й переміщення.
Будь-який залишок — це сума рухів, тож кожну цифру можна розкласти на документи,
а «підправити руками» не можна в принципі. Інвентаризація теж лишає слід:
вона дописує рух на різницю, а не переписує залишок.

Собівартість іде за партіями. Ціна із заявки постачальнику стає ціною партії сировини,
варка збирає спожиті партії плюс накладні й ділить на фактичний випуск,
відвантаження списує конкретні партії — звідси береться реальна маржа за замовленням і за SKU.

Партії підбираються за FEFO (first expired, first out): списується те, у чого раніше
закінчується термін придатності. Для харчового виробництва це правильніше за FIFO.

## Кілька юридичних осіб

Склад фізично спільний, тому власника система веде на рівні **кожного залишку**, а не
складу: у журналі рухів стоїть юрособа, і та сама партія на одній полиці може частково
належати різним юрособам. Кожна веде власну серію нумерації документів зі своїм
префіксом (`ВФ-ЗАМ-2026-0001`), власні залишки, собівартість і розрахунки з ПДВ.
Поточна юрособа перемикається в шапці — усі нові документи створюються від неї.

Продаж власній юрособі — це не переміщення, а реалізація. Позначте клієнта своєю
юрособою на сторінці «Юрособи», і одне відвантаження спише товар у продавця та
оприбуткує його в покупця: партія лишається та сама, змінюються власник і собівартість.

## ПДВ

Ціни в прайсі зберігаються **без ПДВ**, податок нараховується в документі за ставкою
номенклатури — але тільки якщо юрособа-продавець є платником. Неплатник виставляє
рахунок без податку, і в рядку замовлення стоїть нуль.

Головна розвилка — на приході сировини. Для платника ПДВ вхідний податок є податковим
кредитом і **не входить у собівартість**: партія стає на облік за базою. Для єдинника
той самий ПДВ є звичайною витратою і входить у собівартість повністю. Через це одна
поставка дає різну собівартість різним юрособам — і система це показує чесно.
Якщо ж постачальник сам не платник ПДВ, кредиту немає ні в кого.

Уся логіка зібрана в `lib/vat.ts`, щоб не розповзалася по діях.

Зобов'язання й податковий кредит пишуться в реєстр `vat_entries`, звіт за періодами —
на сторінці «Звіти». Виручка й маржа скрізь рахуються від бази без ПДВ: податок іде
транзитом у бюджет і виручкою не є.

Податкове зобов'язання фіксується за датою відвантаження. Для VERDE це і є перша
подія: клієнти працюють на відтермінуванні (мережі 30–45 днів, дистриб'ютори 14),
тож оплата завжди приходить після поставки. Якщо колись з'явиться передоплата,
зобов'язання за нею виникне раніше за відвантаження — тоді знадобиться окрема гілка
в `recordPayment`, яка створює запис зобов'язання на дату оплати.

## Гроші: що куди потрапляє

Правило, за яким живе вся фінансова частина:

| | Фінансовий результат | Борги | ПДВ |
|---|---|---|---|
| **Продаж** | дохід **без ПДВ** | дебіторка **з ПДВ** | зобов'язання окремо |
| **Закупівля** | витрати й собівартість **без ПДВ** | кредиторка **з ПДВ** | податковий кредит окремо |

ПДВ не є ні доходом, ні витратою — він проходить транзитом і ведеться власним
реєстром. У звіті «Фінансовий результат» він показаний лише довідково, разом
із дебіторкою та кредиторкою.

Для неплатника ПДВ «без ПДВ» дорівнює повній сумі: податок постачальника він не
відшкодовує, тож той стає звичайною витратою.

Звіт про фінансовий результат будується помісячно:

```
Дохід від реалізації (без ПДВ)
− Собівартість реалізації (сировина й пакування, без ПДВ)
= Валовий прибуток
− Виробничі витрати періоду (зарплата й енергія цеху)
− Списання й втрати
− Інші операційні витрати (без ПДВ)
= Фінансовий результат
```

Операційні витрати — оренда, зарплата, логістика, реклама — вносяться на тій самій
сторінці. Якщо вказати постачальника, сума з ПДВ потрапляє ще й у кредиторку.

## Виробничі накладні: витрати періоду, а не собівартість

У VERDE електроенергія цеху й зарплата працівників на тимчасовій оплаті **не входять
у вартість партії**. Собівартість партії — це рівно спожита сировина й пакування,
а цех визнається витратою того місяця, коли виник. Тому при закритті варки поля
накладних немає взагалі: технолог вводить лише фактичний випуск і списання.

Це облікова політика, а не константа в коді: у юрособи є перемикач
`overhead_policy` — `period` (за замовчуванням) або `capitalize`. Різниця не
косметична: за `period` прибуток місяця залежить від того, скільки витрачено,
а за `capitalize` — від того, скільки продано.

Щоб при цьому не втратити орієнтир для ціноутворення, на сторінці фінрезультату є
блок **«Довідково: повна вартість одиниці»** — витрати цеху за місяць, рознесені на
випуск за місяць, плюс сировина. Це управлінська оцінка, у проводки вона не потрапляє.
Пам'ятайте, що в місяць з однією варкою вона завищена: увесь цех лягає на цей випуск.

## Запуск локально

```bash
npm install
cp .env.example .env.local        # вкажіть DATABASE_URL і SESSION_SECRET
npm run db:setup                  # міграції + довідники VERDE
npm run dev                       # http://localhost:3000
```

`npm run db:setup` можна ганяти повторно — і міграції, і сид ідемпотентні.

## Наскрізна перевірка

```bash
npm run build && npm start &      # сервер на 3000
BASE_URL=http://127.0.0.1:3000 npm run e2e
```

Скрипт відкриває справжній браузер і проходить повний цикл під чотирма ролями та
двома юрособами: ТОВ на ПДВ закуповує сировину в платника й у неплатника, виробляє
варку з фактичним випуском 980 замість 1000, продає мережі з ПДВ, потім продає частину
власному ФОП; ФОП продає в роздріб уже без ПДВ.

Дорогою скрипт звіряє головне:

- вхідний ПДВ не потрапив у собівартість платника (182,50 з ПДВ → 152,08 на складі),
  а від неплатника ПДВ у собівартість пішла вся ціна;
- та сама партія коштує **12,85 грн у ТОВ і 25,80 грн у ФОП** — бо єдинник не
  відшкодовує податок;
- ціна з прайсу без ПДВ обростає податком саме в документі (29,75 × 640 + 20% = 22 848);
- єдинник не нараховує ПДВ узагалі;
- реєстр ПДВ сходиться: до сплати = зобов'язання − кредит;
- у дохід P&L потрапила сума без ПДВ (25 490), а в дебіторку — з ПДВ (30 588);
- кредиторка перед постачальником — повні 126 500 з ПДВ, хоча в собівартість
  лягло 105 416,71; оплата 60 000 зменшила борг до 66 500;
- оренда 25 000 + ПДВ 5 000 зайшла у витрати базою, а податок — у кредит;
- собівартість партії — **8,57 грн/шт, лише сировина**: поля накладних при закритті
  варки немає, зарплата й енергія цеху зменшили результат окремим рядком і не
  зачепили валовий прибуток;
- управлінська повна вартість одиниці — 33,06 грн проти 8,57 в обліку;
- ролям не видно зайвого.

## Розгортання на Supabase + Vercel

1. Створіть проєкт у Supabase, візьміть `Connection string → URI` (порт 6543, pooler).
2. Локально виконайте міграції проти хмарної бази:
   `DATABASE_URL='postgres://...' npm run db:setup`
3. У Vercel додайте змінні `DATABASE_URL` і `SESSION_SECRET` та задеплойте застосунок.

Схема живе у звичайних SQL-міграціях (`db/migrations/*.sql`), тож переїзд на будь-який
інший Postgres — це той самий `npm run db:migrate`.

## Структура

```
db/migrations/     схема: довідники, журнал рухів, закупівлі, виробництво, продажі, звітні в'юхи
lib/               підключення до БД, сесії й ролі, підбір партій (FEFO), формати
app/actions/       серверні дії — уся бізнес-логіка, кожен документ в одній транзакції
app/(app)/         екрани за модулями
scripts/           міграції, довідники, наскрізний тест
```

## Що свідомо лишилося поза першою версією

- **Реєстрація податкових накладних.** Реєстр ПДВ ведеться, але вивантаження в
  Єдиний реєстр немає.
- **Виключення внутрішніх оборотів.** У зведенні по групі компаній продажі між
  власними юрособами враховані як звичайні, тож чистий результат групи треба
  рахувати вручну.
- Друковані форми (ТТН, видаткова накладна) — зараз дані є, друку немає.
- Інтеграція з Новою поштою та обмін із бухгалтерією (M.E.Doc / 1С).
- Планування виробництва під прогноз попиту — є лише розрахунок потреби під конкретну варку.
- Часткове повернення від клієнта.
